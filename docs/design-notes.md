# Design notes

Решения, которые могут выглядеть спорными при чтении кода, и почему
они именно такие. Не ADR в строгом смысле — просто контекст, чтобы
следующий читатель не «улучшил» защиту в минус.

## Почему mTLS через nginx+re-verify, а не TLS в Python

uvicorn не пробрасывает peer certificate в ASGI scope. Реализовать
полноценный mTLS в Python можно только патчем uvicorn или заменой
ASGI-сервера — это добавляет существенный объём кода и, что важнее,
нестандартную поверхность атаки (патч может разойтись с upstream
и перестать применяться).

**Что делаем вместо:** nginx терминирует TLS, пробрасывает
`$ssl_client_escaped_cert` и `$ssl_client_verify`. Python:

1. проверяет `X-Client-Verify == "SUCCESS"` — defense-in-depth,
   отсекает запросы, если TLS-терминатор не подтвердил handshake с
   клиентским сертификатом (например, кто-то обратился к
   `model-gateway` в обход nginx);
2. верифицирует подпись сертификата через `cryptography`;
3. проверяет EKU, KU, BC, signature algorithm;
4. извлекает SAN DNS как идентификатор. CN как идентификатор не
   используется (RFC 6125 §6.4.4).

**Что это даёт и чего не даёт.**

Даёт:
- Атакующий без `ca.key` не может выпустить сертификат с SAN
  клиента.
- Атакующий без `ca.key` не может подделать SAN в существующем
  сертификате (SAN покрыт подписью CA).
- Скомпрометированный nginx не может подменить SAN в заголовке —
  Python верифицирует сам сертификат, а не доверяет CN-заголовку.
- При обходе nginx (например, при прямом подключении к
  `model-gateway` из соседнего контейнера в `internal-net`)
  заголовок `X-Client-Verify` будет отсутствовать или иметь
  неожиданное значение — запрос отвергается.

Не даёт:
- **Proof-of-possession.** nginx не проверяет, что клиент владеет
  приватным ключом сертификата — это делает TLS-handshake ДО nginx.
  После handshake nginx доверяет `$ssl_client_escaped_cert` и
  пробрасывает его. Если nginx скомпрометирован, он может
  предъявить любой валидный сертификат клиента, которым завладел.
- **Утечка CA.key.** Если `ca.key` скомпрометирован — все гарантии
  рушатся; атакующий выпустит любой сертификат.

**Остаточный риск.** Компромисс nginx + доступ к клиентскому
сертификату (в памяти, на диске, в логах) = подделка клиента.
Этот сценарий требует root-доступа на хосте (для чтения памяти)
или другой критической уязвимости. В модели угроз проекта
(один хост, один оператор, доверенные бинарники клиентов) это
принято как остаточный риск.

**Что было бы полным решением:** ASGI-сервер с завершением TLS в
Python и `ssl.getpeercert()`. Отложено как overkill для текущей
модели угроз. Если модель изменится (multi-tenant, недоверенные
клиенты) — пересмотреть.

## Почему prompt_hash не включает model

`prompt_hash` — HMAC-SHA256 от потока пар `(role, content)` с
length-prefix (4 байта длины + данные). Формат единый для
`/api/chat` и `/api/generate`, чтобы одинаковое логическое
содержимое давало одинаковый хеш:

* chat:    `[(role_1, content_1), (role_2, content_2), ...]`
* generate: `[("system", system), ("user", prompt)]` (system —
  если непустой)

Модель **не входит** в хеш. Это осознанно: один и тот же вопрос
к `qwen3:8b` и `qwen3:1.7b` даёт одинаковый `prompt_hash`, что
позволяет в аудите находить дубли и replay независимо от выбора
модели. Модель пишется отдельным полем `model` в audit-запись;
искать по комбинации `(prompt_hash, model)`.

Length-prefix вместо разделителей выбран потому, что `content`
может содержать любые Unicode-символы, включая управляющие. С
разделителями (`\x1f`/`\x1e`) возникали бы коллизии:
`[("user", "a\x1fuser\x1fb")]` и `[("user","a"),("user","b")]` дали
бы одинаковый HMAC. Length-prefix однозначен при любом content.

## Почему criticality расширений обязательна

`scripts/gateway-certs.sh` выпускает все расширения (BC, KU, EKU,
SAN) как `critical`. Верификатор требует `critical=True` на каждом.

Причина: без этого ручной выпуск сертификата с non-critical SAN/EKU
прошёл бы верификацию. Для оператора, который выпускает сертификат
вручную, обязательность `critical` — якорь политики: любой отход
от предписанного шаблона отвергается. Это в духе проекта: fail-closed
на всех уровнях.

## Почему `USER` в Dockerfile вместо `user:` в compose

Сборка `model-gateway` требует записи в `/app` (`uv sync` создаёт
`.venv`). Если `USER` выставлен до `WORKDIR`/`RUN`, сборка падает
или оставляет `.venv` с неправильным владельцем.

Правильная последовательность: сборка под root → `chown -R` на
runtime-UID → `USER <runtime-uid>` в конце. UID передаётся через
build-arg `RUNTIME_UID`, а не через compose `user:`. Один источник
истины: если compose перекрывает `USER`, `chown` становится
бессмысленным (владелец `/app` ≠ runtime-user).

## Почему CA-срок проверяется на каждом `verify()`

`_check_ca_sanity` в `__init__` проверяет CA-срок один раз при
старте. Контейнер может работать недели без рестарта, и к моменту
истечения CA верификация клиентов начнёт пропускать запросы с
истёкшим CA.

Решение: дополнительное сравнение `now ∈ [CA.not_valid_before,
CA.not_valid_after]` на каждом `verify()`. Стоимость — наносекунды.

## Capabilities gateway-tls

`gateway-tls` работает с `cap_drop: [ALL]` и явным
`cap_add: [CHOWN, SETUID, SETGID]`.

**`SETUID`, `SETGID`.** nginx master запускается от root, читает
`/certs/server.key` (0600, root:root) и сбрасывает worker-процессы
в user `nginx`. Без этих capability nginx не стартует.

**`CHOWN`.** nginx вызывает `chown()` для каждого temp-каталога
(`/tmp/nginx/client_body`, `/tmp/nginx/proxy`, ...) на worker-user.
Это внутренняя логика `ngx_create_paths()` в `src/core/ngx_cycle.c`:

```c
if (chown((const char *) path[i]->name.data, user, -1) == -1) {
    ngx_log_error(NGX_LOG_EMERG, cycle->log, ngx_errno,
                  "chown(\"%s\", %d) failed",
                  path[i]->name.data, user);
    return NGX_ERROR;
}
```

`chown` вызывается безусловно при `worker_user` ≠ `NONE`. Linux
требует `CAP_CHOWN` даже если новый uid совпадает с текущим —
достаточно того, что процесс не владеет файлом.

**Почему не убрать.** Без `CHOWN` контейнер падает на старте.
Альтернатива — `read_only: false` + build-time `mkdir` — ухудшает
security posture сильнее, чем одна capability.

**Blast radius.** `CHOWN` без `SETUID` даёт возможность менять
владельца файлов; но `SETUID` уже позволяет стать любым
пользователем. Дополнительная власть от `CHOWN` — незначительна.

**`NET_BIND_SERVICE` не нужен.** nginx слушает 8443 и 8081 — оба
> 1024. Привилегированные порты не используются.

## Единая политика criticality для всех сертификатов

Все расширения (BasicConstraints, KeyUsage, ExtendedKeyUsage, SAN)
в **любом** сертификате — client и server — обязаны быть `critical`.
`scripts/gateway-certs.sh` их такими и выпускает; `CertVerifier.verify`
и `check_server_cert` это проверяют.

Причина единообразия: две разные политики в одной системе — источник
ошибок. Если бы для server-сертификата criticality была опциональной,
ручной выпуск с laxer-настройками прошёл бы верификацию, а ручной
выпуск client-сертификата — нет. Один и тот же шаблон для всех —
меньше шансов на расхождение.

## Почему ENV HOME=/tmp

`useradd -M` не создаёт домашний каталог. Если не установить `HOME`,
он будет пустым или `/` — и любая библиотека, пишущая в `~/.cache`,
упадёт на read-only rootfs с невнятной ошибкой. `/tmp` смонтирован
как tmpfs в compose, поэтому `HOME=/tmp` — рабочая и предсказуемая
опция.

## Валидация конфигурации при импорте

`gateway.py` загружает конфиг на уровне модуля:

```python
config = load_config(CONFIG_PATH)
```

Это осознанный fail-fast. Альтернатива — ленивая загрузка через
`get_config()` с `lru_cache`, вызываемая в `_startup()`. Плюс
ленивой: импорт модуля не требует env, что упрощает тестирование и
инструментарий (myPy, pylint). Минус: некорректная конфигурация
обнаруживается только на старте приложения, а не при `import`.

Для контейнера с `restart: unless-stopped` разницы на практике нет:
процесс всё равно падает до приёма первого запроса. Выбрано
fail-fast как более явный инвариант.

Env-переменные **все** валидируются в `load_config`:
`GATEWAY_HMAC_KEY`, `GATEWAY_CA_CERT`, `GATEWAY_SERVER_CERT`,
`GATEWAY_SERVER_SAN`, `GATEWAY_SERVER_EXTRA_SANS`,
`GATEWAY_SERVER_IPS`, `GATEWAY_REQUIRE_SERVER_CERT`. Ошибки —
`ConfigError` с указанием переменной. CI-шаг «Import check»
проверяет, что импорт без `GATEWAY_CONFIG` падает с ожидаемым
сообщением, а не молча использует дефолты.

## Почему не ML-классификатор инъекций

**Альтернатива:** обучить или подключить модель, которая классифицирует
ввод и данные как «инъекция / безопасно».

**Почему нет:**

- Ложные срабатывания. Легитимный вопрос «объясни, что означает
  `ignore previous instructions`» — это не инъекция, но похоже.
- Ложные пропуски. Обфускация (`ig\u200bnore`, гомоглифы, ROT13)
  обходит классификатор так же легко, как эвристики.
- Вес. Ещё одна модель в контейнере — это RAM, время старта,
  обновления.
- Ложное чувство безопасности.

**Что вместо:** архитектурная нейтрализация. Любые данные из
инструментов проходят `neutralize_data_block` **безусловно**, теги
ролей экранируются, тройные бэктики заменяются.

## Почему не TLS между контейнерами

**Альтернатива:** HTTPS или mutual TLS между `harness` и
`ollama-runner`, между `harness` и `api-proxy`.

**Почему нет:**

- Угроза — прослушка внутри Docker-демона на хосте. Если у атакующего
  уже есть доступ к Docker daemon, он видит всё и без TLS.
- Прокси и раннер — в одной `internal-net` с `harness`. Сеть помечена
  `internal: true`, наружу маршрута нет.
- Между `api-proxy` и внешним миром — HTTPS уже используется.

**Что вместо:** изоляция сети. `internal: true` надёжнее TLS в этой
модели угроз.

## Почему не GPG-подписи моделей

**Альтернатива:** подписывать веса Ollama GPG-ключом, проверять
подпись перед загрузкой.

**Почему нет:**

- Ollama не публикует GPG-подписи моделей.
- Снапшот `.tgz` + sha256-манифест + staging-volume + отдельный
  updater закрывают основной риск.
- GPG добавляет управление ключами.

**Что вместо:** изолированный `ollama-updater` + снапшот в `.tgz` +
манифест `.snapshot.sha256` + staging-volume. Опционально —
`HARNESS_MODEL_DIGEST` через `ollama list --json`.

## Почему не MCP

**Альтернатива:** подключать инструменты через Model Context Protocol
вместо нативного tool calling Ollama.

**Почему нет:**

- Нативный tool calling Ollama уже поддерживается.
- MCP добавляет процесс stdio, ещё один канал IPC, ещё один слой.
- Секреты между MCP-сервером и харнессом надо как-то передавать.
- Для четырёх инструментов MCP — избыточная абстракция.

**Что вместо:** нативный tool calling. MCP уместен, когда появятся
сторонние серверы.

## Почему метаданные усечения — в атрибутах тега

**Как было:** текстовая метка внутри тела `<tool_result>`.

**Почему переделали:** тело `<tool_result>` должно содержать только
данные. Метка в теле — служебный маркер, который модель могла бы
интерпретировать как инструкцию.

**Как стало:** атрибуты `shown="N"` и `truncated="true"` в
открывающем теге. **Инвариант:** данные в теле, метаданные в
атрибутах.

## Почему `tool_name` убран из tool-сообщения

**Как было:** `{"role": "tool", "content": ..., "tool_name": name}`.

**Почему убрали:** схема Ollama `/api/chat` описывает tool-ответ
как `{"role": "tool", "content": "..."}`. Поле `tool_name` — вне
спецификации.

## Почему `_written_paths` хранит канонические пути

**Как было:** сырые строки, как их вернула модель.

**Проблема:** `"./notes/a.md"` и `"notes/a.md"` — те же inode, но
разные строки. Модель могла записать файл, а затем прочитать его в
той же сессии, используя другой синтаксис пути. Обход
read-after-write.

**Как стало:** `canonical_rel` через `resolve_read` +
`relative_to(workspace).as_posix()`. Тесты
`test_read_after_write_with_*` и `test_read_after_write_end_to_end`
фиксируют инвариант.

## Почему `_wrap_tool_result` принимает `attrs: dict`, а не строку

**Как было:** `extra_attrs: str`, вставлялся без экранирования.

**Проблема:** латентная инъекция. Следующий разработчик мог бы
передать туда пользовательские данные.

**Как стало:** `attrs: dict[str, int | bool]`. Строковые значения и
имена, не матчащие `[a-z_]+`, молча игнорируются.

## Почему `whitelist: []` = «ничего не разрешено»

**Как было:** `policy.get("whitelist") or ["**"]`. Пустой список молча
превращался в «разрешить всё».

**Почему переделали:** расхождение с формулировкой в `fs_policy.yaml`.

**Как стало:** `policy.get("whitelist", ["**"])`. Пустой список —
«ничего не разрешено».

## Почему `fsync` только для критичных событий

**Как было:** `fsync` после каждой записи в `audit.jsonl`.

**Проблема:** на каждом `tool_call`/`tool_result` это реальный I/O,
замедляет отклик.

**Как стало:** `fsync` только для `apply_result`, `session_*`,
`propose_write`, `user_prompt_blocked`, `ollama_error`. В
`gateway.jsonl` — только для `gateway_start`, `gateway_stop`,
`request_rejected`, `rate_limited`, `upstream_error`.

## Почему `uv`, а не `pip + venv`

- `pip` не проверяет хеши без `--require-hashes`, а
  `--require-hashes` не покрывает build-зависимости sdist.
- `requirements.txt` с диапазонами (`>=`) перерезолвится при каждой
  установке.
- `pip` медленный.

**Что вместо:** `uv` с `uv.lock` + `exclude-newer = "7 days"`.

## Почему `sudo docker`, а не членство в группе `docker`

Членство в группе `docker` эквивалентно root на хосте. Любой может
смонтировать `-v /:/host` и читать `/etc/shadow`. Debian wiki прямо
пишет: «членство в группе docker опаснее sudo».

**Как стало:** `sudo docker` в инструкции. В WSL с Docker Desktop
`docker` доступен без sudo — скрипты это учитывают через автодетект.

## Почему `curl | sh` заменён на скачивание + SHA256

`astral.sh/uv/install.sh` — mutable URL. Если endpoint или
release-пайплайн скомпрометирован, выполнится произвольный код до
какой-либо проверки.

**Как стало:** `install-machine.sh` скачивает версионированный
tarball и файл `.sha256` из того же GitHub release, сверяет
`sha256sum -c`, и только потом распаковывает. Fail-closed.

## Почему fingerprint Docker GPG проверяется

GnuPG `--with-fingerprint` печатает fingerprint с декоративным
двойным пробелом между 4-й и 5-й группами; на разных версиях
GnuPG форматирование может отличаться. Сравнение через `tr -s ' '`
схлопывает любые пробельные последовательности в один пробел.

В `install-machine.sh` две проверки: одна при установке Docker
(fail-closed), вторая при уже установленном keyring (warn + ask).

## Почему `chmod 0o644` жёстко зашито в `ConfirmSession.apply`

**Как обычно делают:** оставляют права по umask.

**Почему не так:** поведение становится непредсказуемым. На разных
системах один и тот же код даёт разные права.

**Как стало:** явный `os.chmod(tmp_path, 0o644)`. Файлы, созданные
моделью в `workspace/`, всегда имеют права `rw-r--r--`.

**Ограничение:** если вам нужны другие права — правьте одну строку в
`harness/confirm.py` и пересобирайте образ.

## Почему `alpine:3.19` в `sync-model.sh` по тегу, а не digest

**Как было:** жёстко `alpine:3.19`.

**Почему изменили:** временный контейнер промоушена имеет **rw** на
`ollama-models-verified`. Если тег перезаписан в Docker Hub,
вредоносный код получит доступ к тому с весами модели.

**Как стало:** переменная `ALPINE_IMAGE` с дефолтом `alpine:3.19`.
Для production — `ALPINE_IMAGE=alpine@sha256:<digest>`. Скрипт
печатает предупреждение в stderr с инструкцией.

**Почему дефолт остаётся мутабельным:** жёсткий digest требует
ручного обновления при каждом релизе Alpine и неудобен для
локального эксперимента. Осознанный выбор в пользу удобства с явным
сигналом пользователю.

## Почему TOCTOU в `_tool_list_dir` не закрыт

**Что происходит:** между `p.iterdir()` и `check_read(child_rel)`
каталог может измениться.

**Почему оставлено:** для single-user локальной системы это не
критично: единственный, кто мог бы создать symlink в `workspace/`,
— сам пользователь, вне модели угроз.

## Остаточные риски

* **`log.warning` в `_parse_tool_call` не проходит через
  `_redact_args`.** При malformed tool_call (невалидный `tc`,
  `function=None`, нестроковый `name`) логируется усечённый
  `repr(tc)[:200]` — сырой, без редактирования `content`/`body`/
  `params`. Утечки нет: (а) срабатывает только на malformed входе,
  (б) усечено до 200 символов, (в) идёт в stderr / `docker logs`,
  а не в персистентный `audit.jsonl`, (г) аргументы в тот же момент
  уходят в Ollama — это не новая поверхность. Зафиксировано, чтобы
  будущий аудитор не поднял это как находку.

## Что можно было бы сделать иначе (но не сейчас)

- **Rootless Docker по умолчанию.** Сложнее с GPU.
- **Digest-пиннинг образов по умолчанию.** Затрудняет обновление.
- **`read_only: true` на `ollama-runner` по умолчанию.** Ollama может
  писать в `/root/.cache`, `/root/.config` — включать вслепую риск.
